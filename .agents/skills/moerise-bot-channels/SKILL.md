## 渠道变更

- 分别追踪谁能写笔记、消息从哪里收、定时回顾发给谁。旧 Telegram Chat ID 只指定推送目的地。部署模板首次启动、已有持久设置升级、仅靠部署配置升级走不同入口；改到迁移时，选受影响的入口，带一份停用渠道或不完整草稿验证。
- 切换目的地前入队一个任务，切换后核对它使用的账号、收件人和凭据。覆盖回复和回顾中受影响的任务。更换机器人时核对旧任务的终态及密钥清理，首次绑定后核对已缓存的发送客户端。现成用例见 `internal/notification_channels_test.go` 和 `internal/bot_recovery_test.go`。
- 队列或恢复有变动时，在发生外部写入、尚未拿到回执的位置中断。核对重启后笔记是否唯一、后续消息能否继续、结果不明的分片能否通过「确认已送达」或「补发」续发。涉及游标时用平台事件时间及其精度。涉及限流时按平台实际限制的机器人和会话验证共享冷却。优先扩展受影响的已有用例。
- 从 Core 的同一条记录查到 Web、Android 和 OpenAPI。重点核对连接状态有什么证据、推送能力能否解析出收件地址、发送记录是否在分页前过滤，以及状态允许的人工操作是否在两端都能完成。

## 真实渠道验收

- 按 `docs/DEVELOPMENT.md` 的真实平台入口选择场景。先核对部署、测试账号和平台权限。飞书分别查已发布的收件事件和发消息权限，具体项见 `docs/FEISHU.md`。在受限本地配置或已登录设置页使用凭据和绑定链接；日志只记渠道、步骤、状态及脱敏错误码。
- 对“机器人没回复”，依次确认收到平台事件、Memos 写入作者的私密笔记、回复取得平台回执，记录最早缺少证据的步骤。对定时回顾，按目的地和计划时段核对非空内容及平台回执。私聊回复、定时投递各自留证，群 Webhook 单独核对。
- 普通定时投递可在隔离实例安排几分钟后的真实时段。只有验收目标明确包含跨日或静默窗口，才使用 `quiet_day_qq`。一个渠道失败时，依据已取得的回执缩小复测范围；共享截止时间耗尽后，应先给待测渠道独立时间再判定结果。遇到送达结果不明，先核对目标聊天再补发。
